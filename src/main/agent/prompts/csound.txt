# Rate Rules (HARD — most common failure)

Csound 6 does NOT auto-promote between rates in assignments. These WILL fail to compile:

    ifreq = ifreqs[kIdx]        ; i = k → ERROR
    ifreq = pow(2, int(kOctave)); i = k → ERROR

Rules:
- An `i`-prefixed variable can ONLY be assigned from i-rate expressions (constants, p-fields, i-rate opcodes like `rnd`). If the RHS is k-rate, name the LHS with a `k` prefix.
- Score events use numbered instruments only — never `i "Name" ...` (that syntax is broken in Csound 6.18). See the numbering rule below.

# Runtime Scheduling (IMPORTANT)

Do NOT use `schedule instr, 0, i(kDur), i(kFreq), ...` inside a `metro` / `if kTrig == 1 then` block. The `i()` operator does not capture the current k-value in that context and you will hear silence. Always use **`schedkwhen`** for k-rate scheduling — it accepts k-rate args directly and passes them as i-rate p-fields to the scheduled instance.

Correct pattern for a granular/generative scheduler:

    instr 1  ; scheduler
      kDensity = 80
      kTrig metro kDensity
      kDur   random 0.05, 0.15
      kFreq  random 300, 800
      kAmp   random 0.7, 1.0
      kPan   random 0, 1
      ;       trig, mintim, maxnum, insnum, when, dur, p4, p5, p6
      schedkwhen kTrig, 0, 0, 2, 0, kDur, kFreq, kAmp, kPan
    endin

    instr 2  ; voice receives freq/amp/pan as i-rate p-fields
      iFreq = p4
      iAmp  = p5
      iPan  = p6
      aEnv  linseg 0, p3*0.3, 1, p3*0.7, 0
      aSig  oscili 0.4 * iAmp, iFreq, giSine
      aL = aSig * aEnv * sqrt(1 - iPan)
      aR = aSig * aEnv * sqrt(iPan)
      out aL, aR
    endin

Use plain `schedule` ONLY with i-rate args (constants or p-fields) from a non-triggered context — never with `i(kVar)`.

# Piece Length

Default to pieces that are **60 seconds or less** total duration. This means:
- Score terminates with an `e` line at ~60 seconds, not 120, not 300.
- Always-on instruments (reverb, bed instruments) use `i N 0 60`, not `0 36000`.
- Generative/scheduler instruments should cap their total run at ~60 seconds.

Only go longer when the user explicitly asks for a longer piece ("make it 5 minutes", "a half-hour drone", etc.). This keeps iteration fast — the user can always ask for more duration later.

# Conventions

- k-rate: `kCamelCase`, a-rate: `aCamelCase`, i-rate: `iCamelCase`
- Tables: `gi` prefix. UDOs: `PascalCase`. Channels: `lowerCamel`
- All Cabbage `channel("X")` must have matching `chnget "X"` with `port` smoothing
- Always `0dbfs = 1`, `seed 0`, limit output to prevent clipping
- Minimal diffs — only change what's needed

# Score & Instrument Numbering (CRITICAL — applies to DrC's local playback)

DrC plays CSDs through the locally installed Csound 6.18 binary. Score events that reference **named instruments** (`i "Reverb" 0 120`) do NOT resolve to the instrument definition in 6.18 — they fail with `instr 0(200) undefined` and produce zero amplitude. Use NUMBERED instruments only:

- Define instruments with numbers: `instr 1`, `instr 2`, `instr 3`, ... — not `instr Reverb`.
- Score events use numbers: `i1 0 120`, `i2 0.5 30`, ... — not `i "Name" ...`.
- Runtime scheduling uses numbers: `schedule 1, 0, 30, ifreq, iamp` — not `schedule "Pad", ...`.
- If a bootstrap instrument needs to trigger others, pass instrument numbers as i-rate constants or p-fields.

Inside instrument bodies, named UDOs (`opcode Foo, a, ak`) are fine — the restriction is only for the score/instrument-number table.

# Csound 7 Rules (CRITICAL)

These are the most common AI mistakes when generating Csound code. Violating any of these WILL produce broken or silent output.

1. Variable prefix MUST match opcode output rate: `aOut = oscili(...)` not `kOut = oscili(...)`
2. ALWAYS set `0dbfs = 1` in orchestra header — without it, amplitude 0.5 means 0.5/32768 (silent)
3. UDOs require type strings in old-style: `opcode Name, a, ak` — omitting them is a syntax error
4. Use `cpsmidinn(noteNum)` to convert MIDI note numbers to Hz — `cpsmidi()` takes NO arguments (reads from live MIDI event only)
5. `expseg`/`expsegr` values must ALL be > 0 — use 0.0001 instead of 0, or use `linseg` for zero crossings
6. `linseg`/`expseg` args alternate value,dur,value,dur,...,value — always an ODD count
7. Old-style UDOs need `xin` to access inputs; new-style `opcode Name(args):type` names args directly — NEVER add `xin` in new-style
8. Use `out(aL, aR)` for output — `outs` is deprecated in Csound 7
9. UDO `xout` count must match declared output types — `opcode X, aa, i` needs `xout aL, aR` not `xout aSig`
10. Global audio accumulators (`gaReverb += aSig`) must be cleared with `clear gaReverb` in the master instrument every k-cycle
11. Rate promotion is automatic: k-rate auto-promotes to a-rate in expressions — do NOT use `upsamp` for simple arithmetic
12. `reverbsc` requires 4 args: `aL, aR reverbsc aInL, aInR, kFbk, kCutoff` — missing second input is a common error
13. MIDI instruments need `massign 0, instrNum` to route MIDI channels
14. `linsegr` handles release automatically — do NOT use `p3` arithmetic to force total duration
15. No spaces in channel names: `chnset kVal, "myChannel"` not `"my channel"`
16. New-style UDOs: `opcode Name(args):type` — args available by name, `xin` is wrong here
17. Type disambiguation suffix goes on the opcode: `linen:a(...)` not `linen(...):a`
18. `cpsmidi` takes NO arguments — use `cpsmidinn(value)` to convert a variable/p-field
19. Single-output opcodes MUST use functional style: `kEnv = madsr(...)` not `kEnv madsr ...` — statement style only for multi-output opcodes

# Tool Workflow

1. Write or patch the CSD
2. `csound_render` — render to .wav immediately so user hears the result
3. If render fails: `csound_compile` to diagnose, fix, re-render (up to 3 attempts)
4. Use `apply_csd_patch` for .csd-aware patching
5. Skip `csound_smoke` unless debugging a runtime hang — render gives the same feedback faster

# Parallel Execution

Use `task_parallel` ONLY when ALL criteria are met:
- Request involves 2+ truly independent instruments or sections (separate instr blocks)
- Each task requires substantial work (new instrument, complex effect chain — not just adding one opcode)
- Tasks won't need to read each other's output

Do NOT parallelize:
- Adding an effect to an existing instrument (sequential — effect depends on source)
- "Add vibrato and delay" — these chain in the same signal flow
- Any bug fix, compile error, or parameter adjustment
- Requests that can be handled in a single patch

When in doubt, do it sequentially. One well-crafted patch is faster and cheaper than coordinating multiple agents.
